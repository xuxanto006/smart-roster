### 二、修 bug：间歇性违规（关键教训：先量，别猜）
**错误的第一次猜测**：以为是 `fillGaps` 后处理破坏了分组保障。
探针 `diag_where.js` 证明无辜（introduced=0, fixed=0）。

**真正的根因链**，逐步量出来：
1. 选优字典序第一键 `gap` 把 12 个「富余人力槽位」也算成缺口
   → 「155 槽位全填满但有 1 条分组违约」压过「分组全对、富余空 1 格」。
   修：`demandNeed/demandKeys` 只认真实需求。
2. 分组休息日没上限 → 某组当天休太多人，物理上凑不齐保障班次。
   修：`groupRestOK()` 放到「分配休息日」**之前**。
3. `fixGroupShortage` 补早班时会拆掉同组的晚班，来回震荡。
   修：`wouldBreakOtherGroup()`。
4. **`planIsoRest` 用 `plan.restDays`（分配阶段记录的集合），与最终 `assign` 脱节。**
   某人少排一天班 → 界面上那天就是休息日（实际休 3 天），但集合里只有 2 天
   → 选优误判「无上一休一」，把带病方案选成最优。这是「每人休 3 天」的真凶。
   修：改成按 `plan.assign` 算真实休息日。
5. 新增 `absorbPlan(plan, R)`：在**评分之前**先把富余人力吸收掉（空闲日补中班/晚班，
   绝不碰人数固定的早班），让评分看到的班表 = 最终写进界面的班表。
   配套 `absorbSurplus(week, R)` 在写表后再补一刀（`repatchWeek` 也接了）。
6. 副作用修复：`capacity` 原先硬编码 `N*5`，改为跟随 `restMax.per`。

**踩过的坑**：以为「减少休息日」不会制造孤立休息日 —— 错。
休{五六日} → 把周六改成上班 → 周五和周日被周六隔开，成了 休-上-休。
两个吸收函数都加了「试排后比对孤立数，只允许不增」。

### 三、性能与质量权衡
- `absorbPlan` 让第一个候选就满足全部硬条件 → 提前退出在第 1 个就触发 → 121ms，
  但没机会在多个合格方案里挑最均衡的。加 `MIN_POOL = 40`。
- 实测（31 人）：早/晚班次数标准差在池子 20/40/80 下是 0.71/0.75/0.73、0.88/0.86/0.86
  → **班次均衡度是贪心的结构性上限，多跑没用**；
  真正随池子收敛的是「连休对数」1.2 → 0.4 → 0.3 对/周（设计要求休息日不连续）。
  取 40：连休 0.4 对，单次排班 ~450ms（修复前 3954ms）。

## 第三轮 —— 新增「📌 固定上班日」常驻规则（已部署）

### 需求
用户：「规则增加：周一陈悦娴，张淑慧这两个人必须上班」

### 做法：做成常驻规则，而不是塞进请假列表
新字段 `state.mustWork = [{name, day}]`，默认预置 陈悦娴/张淑慧 周一。
在 `buildRules()` 里编译成 `noOff`（与请假区的「必须上班」同一条约束），
所以排班算法、实心高亮、微调、导出全都自动生效，一行算法都不用改：
```js
(state.mustWork || []).forEach(mw=>{
  const c = row[mw.day];
  if(!c || c.off) return;   // 当天请假 → 请假优先，不强制上班
  c.noOff = true;
});
```
存档：`save()` 增加字段；`load()` 里 `Array.isArray(o.mustWork)` 时才整体替换
（老存档缺字段 → 保留默认预置；用户删空 → 就是空，不会被默认值填回来）。

## 第 4 轮：「上一休一」违规归因 + 🩺 本周体检面板（已上线）

  对已合规班表是真·空操作。我此前「微调改坏了」的判断是**错的**，已纠正。

### 归因：100% 是输入层规则撞车，不是算法缺陷
- `probe_leave.js`（6 个样本）全部同形：同一个人请了**两天不相邻**的假
  （例：邓臻蓝 周二+周日 → 休{二,日} → 周三~周六上班 → 数学上躲不开「休-上-休」）。

  `出现上一休一 9/200 轮` / `休息日全部由请假钉死（不可避免）9 人次` /
  `含算法自选休息日（算法问题）0 人次` / `其它违规 0 条`。

- 检查**结果层**：每天各班次缺口 / 每人休息天数 / 上一休一 / 超班次上限 /

## 第 5 轮：矛盾预检提前到「录入规则时」（已上线）

- 关键坑：休息日不只被「请假」钉死，也会被「必须上班」挤到只剩固定几天。
  初版只传 offDays 漏了这条，补 `mustDays` 参数后覆盖。

## 第 6 轮：全规则审计 + 修掉体检面板一处「假绿灯」（已上线）

### 做法：先审计，而不是继续加功能
`audit_all_rules.js`（新建）：把用户从第一轮到现在提过的**每一条规则**逐条跑，
各计违规次数。17 项检查（班次需求 / 工作日早班恰好 8 人 / 早≤3 晚≤4 / 每人休 2 天 /
全队休息上限 / 上一休一 / 三连早 / 晚接早 / 早晚保障组每天 1 早 1 晚 /
开店闭店每天 1 开店 2 闭店 / 开店闭店每人 ≤3 次 / 周末连上早班 ≤1 人 /
开店闭店组周末换人 / 请假与改班）。
- 无请假 150 轮：**17/17 零违规**。
- 带请假 300 轮：只剩「上一休一」（预检已判定不可避免）与一次开店闭店缺口。

### 用最大流给「开店闭店填不满」定案
`probe_close.js` / `probe_close2.js`（新建）：把「每天 1 开店（该组当天早班者）
+ 2 闭店（该组当天晚班者）、每人每周 ≤maxPerWeek 次」建成最大流，看能否流满 21。
- 500 轮：填不满 2 轮，**两轮最大流都只能到 20/21 → 本身就凑不出，算法问题 0**。
  `assignRoles` 是最优的，不用改。
- 成因细分（cap=3 vs cap=99 各算一次）：
  - 可用性不足（某天该组上班次的人就不够）→ 体检面板现有检查能抓到
  - **额度不足（人够，但 ≤3 次分不过来）→ 体检面板抓不到，会显示「全部通过」**

### 修掉的真缺陷：体检面板的假绿灯
`renderHealth` 原先只数「当天该组有几个人上早/晚班」，不看这些人的 ≤3 次额度还剩多少。

  - 该组当天只有 N 人上早/晚班 → 说人数不够
  - 当天有 N 人上，但额度用完 → 说「每人每周≤3次」额度已用完

## 第 7 轮：配置敏感度扫描（可调旋钮的安全范围）

### 起因
前 6 轮所有审计都只在**默认配置**下跑过。但工作日早班人数、休息天数、班次上限、
开店闭店次数上限都是用户可调的，拧到别的值会怎样从没验过。

### 方法
`sweep_configs.js`：一次只改一个参数，13 个配置 × 20 轮 × 17 条规则检查。
并新增 `configWarnings(cfg)` —— 用空班表调 `renderHealth`，
看**改完配置、还没排班时**面板有没有把「这个配置排不出来」说出来。

### 结论（✅ 安全旋钮 / ⚠️ 会塌的旋钮）
| 配置 | 结果 |
|---|---|
| 基准 / 休1天 / 早班=6 / 早班上限=4 / 周末上限=0 / 周末上限=2 / 开店闭店≤4 | ✅ 全通过，面板不响 |
| 每人休 3 天 | ⚠️ 面板已提示（人力不够：需求143 > 31×4=124） |
| 工作日早班 = 10 | ⚠️ 已提示（需求157 > 155） |
| 早班上限 = 2 | ⚠️ 已提示（早班需求58/产能62，已用94%） |
| 开店闭店每人 ≤ 2 | ⚠️ 已提示（**本轮新增的检查**） |
| 全队休息上限 = 55 | ⚠️ 已提示（55 < 31×2=62） |
| 晚班上限 = 3 | ⚠️ **仍静默**（总量宽松：晚班74/93=80%，组晚班人日14/27=52%，聚合指标算不到逐日组合问题） |

### 本轮修的真问题：分组产能静默
「开店闭店每人 ≤2 次」时 9×2=18 < 7×(1开店+2闭店)=21，**数学上必然差 3 个名额**，
但原界面毫无提示（全队层面的检查算不到组里）。
→ 在 `renderHealth` 加了 `capCheck(label, need, cap, unit)`：
超了报 ❌「必然排不出来」，超过 85% 报 ⚠️「余量很紧」。
覆盖：开店闭店组角色名额 / 早班人日 / 晚班人日，早晚保障组早班人日 / 晚班人日。

### 「上一休一」成因判别（重要方法论教训）
扫描发现每个失败配置都带「上一休一 · 本可避免」，默认配置是 0。追查过程：
1. **第一次判断方式错了**：把 `planScore` 里 isoRest 权重临时拉到 10 万，看能不能降到 0
   （`probe_iso_config.js`）。结果几乎不动（34→27），一度误判为「配置本身排不出来」。
   **错因**：iso 在选优里是**字典序硬约束** `badNow = planIsoRest + planGroupViol`，
   排在第 3 位、压过 `score`。调 score 权重根本轮不到被比较 —— 无效杠杆。
2. **换从后处理这条线查**（`probe_isosrc.js`）：逐个关掉最终班表级的
   `absorbSurplus` / `fillGaps`。41 → 35 → 31 → 29，后处理只解释 12/41。
   → 主因是**候选搜索本身没找到干净解**（早班上限=2 时，
     「上一休一」+「早晚保障组每天1早」两个约束叠加后几乎没有回旋空间）。
3. 单独验算「上一休一」本身不构成阻塞：7 天里允许的休息日配对有 14 种
   （循环距离 1 或 3，(d,d+2) 是唯一禁形），4-正则图容量足够。
   → 是**联合约束太紧**，属配置撞车，不是算法错。默认配置 0 例，线上不受影响。
   → 决定**不改算法**，按「不要擅自更改规则」列为已知限制。

## 第 8 轮：微调路径审计 + 提示文案假成功修复

### 起因
前 7 轮的全规则审计只跑过「一键排班」（全局搜索）路径。但用户日常最常用的是
「排完班 → 临时加请假 → 点🔄微调」（`repatchWeek`，局部修复），这条路径
`probe_repatch.js` 只查了 5 项，17 条规则里还有 9 条从未验过。

### 核心发现：微调显著劣于重排（同输入对照，`audit_repatch.js`）
| 请假条数 | 微调出问题的轮次 | 重排出问题的轮次 |
|---|---|---|
| 1 条 | 15/40（38%） | 0/40 |
| 2 条 | 25/40（63%） | 0/40 |
| 4 条 | 32/40（80%） | 0/40 |

违规类型：上一休一 7、晚接早 5、三连早 3、闭店缺 2、保障组缺晚 2、开店缺 1 等。
**重排在同样输入下 0 违规 → 这些全部可避免**，不是规则撞车，是局部修复没有全局搜索的自由度
（`fillGaps` 补位时不检查三连早 / 晚接早 / 上一休一）。
新增第 15 条检查「角色标记与班次一致」结果 0，说明 `syncRoles` 机制是好的。

### 为什么没有改成「微调失败就自动整体重排」
差点这么做了，但先查了调用点才发现 `test_mustwork_repatch.js` 有断言守着设计意图：
**微调是「轻触」策略，不覆盖手动改过的格子**。自动回退到 `autoSchedule` 会把手动调整全冲掉，
测试会失败、也违背用户早前定下的行为。
→ 改为：保留轻触，只修「提示文案」。
→ `copyPrevWeek` 走 `repatchWeek(true)`（silent），用 `!silent` 守卫可精确避开。

### 修的真问题：提示文案假成功
`repatchWeek` 只用 `bad`（请假满足）+ `still`（缺班）判定成败，
三连早 / 晚接早 / 上一休一 / 开店闭店缺人 / 周末连上早班 / 全队休息超限全部不在判定里
→ 35% 的轮次藏着违规，提示却写「✅ 全部安排已满足，其余人班次保持不变」。
体检面板其实 **14/14 全覆盖、漏报 0**（`probe_repatch_panel.js` 验证），
所以用户没被完全蒙住，但按钮提示和面板互相打架。

**改法**：新增 `patchViolations(week, R, k)` 做完整自检，成败判定改以它为准。
覆盖：缺班 / 请假改班 / 上一休一（剔除输入层不可避免的）/ 三连早 / 晚接早 /
班次超上限 / 保障组缺早晚 / 开店闭店缺 / 周末连上早班 / 全队休息超限。
口径刻意与 `renderHealth` 的 errs 对齐，避免「面板报冲突、提示说没事」。
只改提示不动班表：改动前后微调违规数 38/30 轮、63%，**完全一致**。

### 我自己写错的三个测试断言（都不是代码问题，修测试）
1. 独立审计漏查「缺班」→ 把「提示报缺人」误判成误报
2. 独立审计漏查「保障组缺晚」→ 同上
3. **三连早只查了 d=0..4**：`hasEarlyRun3` 是**跨周循环**的
   （`d, (d+1)%7, (d+2)%7`，d=0..6），「周六日一」也算三连早。审计口径窄了。
4. 另一条「手动改的 6 处格子必须 100% 保留」过死：可能撞上后加的请假条。
   改成「整张表保留率 > 90%」（实测 97.7%），这才是「没被换成整体重排」的可靠代理指标。
