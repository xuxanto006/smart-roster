## 排班系统三条新规则 —— 稳定性收敛（收尾）

### 背景
用户在 `app_merged.html` 上提出三条新规则：
1. 休息配额改为区间（1-2 / 2-3 天可调）；休 3 天时禁 3 连休，可 2 连休 / 单休
2. 专家老师组每天保证 1 早 + 1 晚
3. 模块不得全员休息，至少 1-2 人在岗

功能已实现，本次会话专攻**稳定性**（多条规则互相顶死导致的偶发违规）。

### 修复前的失败率基线（8 轮 × 9 配置 = 72 次排班）
专家组 5 / 模块 7 / 3连休 0 / 区间 0

### 定位到的根因（4 个独立 bug）

**① fixGroupGuarantee 缺跨天腾挪能力**（专家组修不掉，主因）
前四条路径全部只在「当天这一格」上打转。实测样本：周日缺早班时 4 名组员被
「周末连早 / 连三早 / 早班超上限(3/3) / 晚接早」各挡一种，全部无解 ——
不是路径写得不对，是根本没给它们跨天操作的手段。

新增**第五条路径：跨天腾位补缺**
- A 在 x 天让出 shA（x 是挡住 A 的那天），C（x 天休息）顶上去
- A 空出来去 d 天补缺口
- 第 x 天每班次人数不变（C 精确顶上），第 d 天缺口 +1
- 与 fixRun3Rest 第三条路径同源思路

注意：**第一版设计错了** —— 写成「找一个当天也在上同一班次的人跟他对调」，
但触发场景恰恰是当天该班次一个人都没有，候选恒为空。已修正。

**② fixRestRange「休少了」分支逻辑写反 + 从未赋值**
代码在「n 已休息」的日子里找，且找到候选人后只 `fixed++; didAny=true; break;`
**一行赋值都没有** —— `week[n][d]` 从未被改。后果：didAny=true 让外层以为修好了，
实际班表纹丝不动，白耗 20 轮 pass。且语义本身反了（休少了应该**多休**，不是多上班）。

**③ fixModuleAllOff 对调是单向的**
注释说「B 则接过 A 的某个休息日」，代码只写 `week[B][d]="rest"`，
B 并没有去 A 的休息日上班 → A 白少休一天、B 白多休一天，全队休息总数失衡。
且 B 用 `staff.find` 取第一个就 break，不做任何可行性检查。

重写为**双向对调**：A 在 d 顶 B 的班 + B 去 A 的休息日上班，两人各一进一出。

**④ fixModuleAllOff 缺第二条路径**
重写后仍剩一种形态无解：A 只休 1 天（就是缺口那天），没有「另一个休息日」可让。
（1~2 配额下 2-3 人小模块最容易撞：两人休息日撞同天，且谁都只有 1 天可休）

新增**第二条路径：跨天腾位补缺**（与专家组路径5 同源）
- A 在缺口日直接上班（挑不限人数的班次）
- A 在自己某个工作日 x 上让位给休息中的 C

## 追加：路径5 的守恒判据实验（已回退）

为修最后那 0.28% 的专家组偶发失败，改写了路径5 的复核判据：

**错误做法**：要求「每天每班次人数逐一相等」。
—— 这等于**禁止填补缺口**：触发场景恰恰是 d 天该班次一个人都没有
（early=0），此时任何「补位」都会让该班次人数 +1，被这条判据一票否决。

**第二种错误做法**：放宽为「不超过需求上限即可」。
—— 实测 en 1→2、mod 0→2，引入新违规（撑爆别人班次名额）。已回退。

**最终回退到 path5v1 的严格守恒版**（要求同班次对调、人数逐一相等）。

后续若要再攻这 0.28%，正确方向是**多级连锁**而非放宽判据：
孙勇 `[N N . E N . E]` 卡在「晚接早(周二晚→周三早)」——
障碍是周二，但他的早班在周四、周日，让位点与障碍点不重合。
需要的是「A 让 x → C 顶 x → C 自己也得再让 y → D 顶 y」的链式腾挪，
单级对调结构上覆盖不到。

## 性能优化（回归测试跑 54 分钟触发的）

**问题现象**：`test_edge.js` 单个套件跑 1379 秒，整套回归 54 分钟。

**定位过程**（写了分段计时探针，逐函数累计耗时）：
- `tryPlan` 1124ms / 198 次调用
- `balanceShifts` 1102ms / 8 次调用 ← 老代码，但我今天加的重试机制让它跑得更多
- `fixGroupGuarantee`（我写的路径5）**只有 1ms，完全无辜**

**根因**：我今天做的两件事叠加放大：
1. `allPlans` 候选池 24 → 40 → `tryPlan` 多跑 60%
2. 重试机制「最多试 12 个候选」→ `materialize` 多跑 → 每次都带两遍 `balanceShifts`

**三档配置实测对比**：

| 配置 | 耗时 | en | mod | r3 | range |
|---|---|---|---|---|---|
| 40 / 2500ms / 12次600ms | 2580ms | 0 | 0 | 0 | 0 |
| **40 / 1600ms / 10次450ms** | **2189ms** | **3** | **0** | **0** | **0** |
| 24 / 900ms / 6次250ms | 1928ms | 3 | 3 | 0 | 0 |

**取中间档**：`test_edge.js` 1379s → 15s（92 倍加速），模块/3连休/区间保持 0 违规。

**关键发现**：剩下那 0.8% 的专家组缺口**与候选池大小无关** ——
40 和 24 都是 3 次。说明不是「候选不够多样」，而是路径5 的单级严格守恒对调
结构上覆盖不到「让位点与阻碍点不重合」的形态（孙勇 `[N N · E N · E]` 卡在
「晚接早(周二晚→周三早)」，但他的早班在周四、周日，让位点与障碍点不重合）。
再加候选也换不出来，要修得做**链式腾挪**（A 让 x → C 顶 x → C 再让 y → D 顶 y）。

**教训**：优化性能前先测热点，不要凭直觉改。
`fixGroupGuarantee` 写了 200 行嵌套循环，直觉上它最慢，实测只占 1ms。

## 追加：行政 5 人改为「固定班表」（周一~周五早班 + 周末双休）

黎瑶、杨乐乐、莫甄姗、刘可佳、何昊敏 —— 不再是「暂免」，而是**有确定班次**。

**新增机制 `fixedRoster`（state.fixedRoster）**
```js
fixedRoster: { admin: { roster: { "黎瑶": [早,早,早,早,早,休,休], ... } } }
```
与既有概念的区别（这是设计关键）：
| | 含义 | 界面 |
|---|---|---|
| 免排 EXCLUDE_* | 完全没有班次 | 标「暂免」 |
| **固定班表 fixedRoster** | **有确定班次，只是不由算法分配** | 正常显示格子 |

落地方式：`applyFixedRoster(week, R, dom)` 在**整张表排完、收尾修复之后**覆盖格子。
放在最后是有意的 —— 修复器可能改到这些格子，但用户要的是「每周都这样」，不该被均衡度优化改掉。
**请假仍然优先**（内部跳过 `c.off` 的格子），与界面提示一致。

## 踩坑：固定班表的人不能进算法人力池

第一版只把「行政」从 `EXCLUDE_MODULES` 移除，结果 **5 个回归套件挂了**
（test_leave_nolimit / test_out / test_offday / test_limin / test_dated_req），
现象是 **3c 整周排不出班表（全是空格子）**。

根因：`isBlockedFromSchedule` 放行他们之后，他们进了 `state.staff`（算法人力池）。
算法以为多了 5 个可用人力 → 产能计算失真 → 排出「排不满」的班表 → 整周空。
（测试里 `S.staff = DEFAULT_STAFF.filter(可排班).slice(0,20)` 正好把行政的人捞了进来。）

**正确做法**：`isBlockedFromSchedule` 里保留「判为不可排班」：
```js
if(fixedRosterNames("admin").indexOf(name) >= 0) return true;
```
因为他们的格子由 `applyFixedRoster` 直接写，不依赖这套判定。
**「有确定班次」与「参与算法分配」是两件事** —— 这是最容易搞混的点。

另外 `autoSchedule` / `repatchWeek` 里也加了一道 `allFixedRosterNames()` 过滤，双保险。

## 另一个坑：固定班表部门不必跑算法

行政域的需求表是按「算法排班」口径设的（早3/中1/晚1），但这些人只上早班。
跑算法必然弹「覆盖 10/23 个班次」「开店闭店还缺 21 人次」这类**必然发生**的警告。
→ 加了快速通道：有 `fixedRoster` 的领域直接写盘返回，弹「已按固定班表排好」。
